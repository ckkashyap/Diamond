Diamond OS

A small bare-metal operating system for 64-bit PCs — explained from first principles, with the real code, so you could build it yourself.

A literate-programming walkthrough. Every idea is introduced before it is used, every unfamiliar word is defined the first time it appears, and the code you read here is the code that actually runs. Target reader: a curious high-school senior who has written a little C.

1Start here

This document teaches you how a real computer goes from the instant you press the power button to a working, interactive operating system that draws text on the screen, reads your keyboard, uses all of your CPU cores, plays sound, and even runs a little ray tracer — with no Windows, Linux, or macOS underneath it. Just your code, talking to the bare hardware.

🧭What "literate programming" means The idea (from computer scientist Donald Knuth) is to write a program as if it were an essay for a human, with the source code woven into the explanation — instead of writing code for the machine and adding comments as an afterthought. So this is not documentation about Diamond; it is Diamond, retold in the order that makes it easiest to understand.

1.1  What is Diamond?

Diamond is an operating system — but a very small and unusual one. When you turn on a PC, some program has to be the very first thing that runs and takes charge of the whole machine. Normally that program is Windows or Linux. In Diamond, it is about six thousand lines of C that we wrote ourselves.

It boots on a real or virtual 64-bit Intel/AMD PC and gives you a text prompt:

Diamond OS
Command> raytrace
[cpu0] 90 lines  [cpu1] 90 lines  [cpu2] 90 lines  [cpu3] 90 lines
rendered 720 lines on 4 CPUs in 141 ms  (3.9x speedup)
Command> _

From that prompt you can print how much memory you have, list your CPU cores, draw graphics, run a multi-core ray tracer, play a piano with the mouse, and reboot the machine. All of it is code in this walkthrough.

📖New term Operating system (OS). The master program that controls a computer: it takes over the hardware when the machine starts, and provides everything else that runs with a way to use that hardware (screen, keyboard, memory, disks, network). Diamond is an OS in this literal sense — it is in charge of the whole machine — even though it is tiny compared to Windows.

1.2  What you will be able to build

By the end you will understand — well enough to re-create — each of these pieces:

  • A bootable kernel. The single program that the firmware loads and jumps into.
  • A memory allocator — your own malloc()/free(), because there is no operating system beneath you to provide one.
  • A graphics driver that writes colored pixels straight into video memory.
  • A font renderer that turns a real TrueType font file into pixels, and a terminal that scrolls text like a console.
  • A keyboard driver — several of them, actually, behind one clean interface.
  • Multi-core support: waking up the other CPU cores and giving them work.
  • Sound, from a simple beep to pitch-shifted piano samples.
  • A shell (the Command> prompt) and a few showcase programs.
  • And, as a finale, a synthetic keyboard driver for Microsoft's Hyper-V — the trickiest piece, because a modern virtual machine has no old-fashioned keyboard to talk to.

1.3  What you need to know first

You should be comfortable with the basics of the C programming language: variables, if/while/for, functions, arrays, and especially pointers (a variable that holds the numeric address of another piece of data). If you have written a program that uses int *p; *p = 5;, you know enough to start. Everything specific to operating systems and to the Intel/AMD hardware — and there is a lot of it — is explained here as we meet it.

A few C reminders that we lean on constantly:

  • uint8_t, uint16_t, uint32_t, uint64_t are integers of an exact size: 8, 16, 32, or 64 bits (a bit is a single 0-or-1; 8 bits make one byte). We use exact sizes because when you talk to hardware, the size matters.
  • A hexadecimal number is written with a 0x prefix, e.g. 0xFF = 255. Each hex digit is exactly 4 bits, which makes hardware addresses easy to read.
  • The bit operators & (and), | (or), ^ (xor), ~ (not), << / >> (shift left/right) let us set and test individual bits. Hardware is controlled almost entirely by flipping individual bits.
  • A pointer holds an address. If a specific hardware register lives at address 0xB8000, then volatile uint32_t *reg = (uint32_t*)0xB8000; lets us read and write it as if it were an ordinary variable.
📖New term volatile. A C keyword that tells the compiler "this memory can change on its own, and every read/write I wrote must really happen — do not optimize any of them away." Ordinary variables can be cached in registers or reordered by the compiler; hardware registers cannot, because reading them can have side effects and their value can change because the device changed it. We mark every pointer that points at hardware volatile.

2The big picture

Before any code, you need the shape of the whole thing in your head. Two ideas make Diamond what it is, and almost every design choice later follows from them. This chapter explains both, then shows the path the computer takes from power-on to your code.

2.1  An operating system with no operating system underneath

When you write an ordinary program — a game, a web browser — it does not really talk to the hardware. It asks the operating system to do things on its behalf: "open this file," "put this window on screen," "give me more memory." Those requests are called system calls. The OS sits between every program and the hardware, sharing the machine safely among many programs and protecting them from each other.

Diamond throws that arrangement away. There is exactly one program — Diamond itself — and it is the thing talking to the hardware. There is no layer beneath it to ask. When Diamond wants to draw a pixel, it writes the pixel's color directly into the memory the graphics card is displaying. When it wants a keypress, it reads the keyboard's hardware directly. This style is sometimes called an exokernel or an "OS as a library."

Three consequences fall out of this, and they run through the entire codebase:

  • A "driver" is just a normal C file. The keyboard driver, the video driver, the sound driver — each is a handful of functions compiled into the same program. There is no plugging in, no loading; they are all simply there, linked together into one file.
  • The shell is just a function the kernel calls. When Diamond finishes starting up, it calls shell_run() the way you would call any function. The Command> prompt is not a separate program; it is a while loop inside the kernel.
  • There are no permissions to cross. Everything runs at the CPU's most-privileged level, so any part of Diamond may touch any piece of hardware at any time. Powerful, and unprotected — exactly the trade a teaching OS wants.
📖New term Privilege level (ring / CPL). Intel/AMD CPUs can run code at four privilege levels, numbered 0 (most powerful) to 3 (least). Ring 0 is often called "kernel mode"; ring 3 is "user mode." Normal apps run in ring 3 and must ask the ring-0 kernel for anything dangerous. CPL means "Current Privilege Level." Diamond runs entirely in ring 0 (CPL 0): it never drops to ring 3, so it never has to cross a privilege boundary. That is why it needs no system calls.
⚠️This is a teaching design, not a safe one Real operating systems keep apps in ring 3 precisely so a buggy or malicious program cannot scribble over the kernel or another app. Diamond has none of that protection — a stray pointer can corrupt anything. That is an acceptable price for a system whose goal is to be understandable, and whose only "apps" are the demos we wrote ourselves.

2.2  The one big rule: everything is polled

Here is the single most important rule in Diamond, the one that shapes every driver you will read:

Diamond never lets the hardware interrupt it. Instead, Diamond repeatedly asks the hardware whether anything has happened. This is called polling.

To see why that is a real decision, you need to know the normal alternative.

📖New term Interrupt. A signal a hardware device sends to the CPU to say "stop what you are doing right now and come deal with me." When a key is pressed, the keyboard can raise an interrupt; the CPU instantly jumps to a special function called an interrupt handler to service it, then resumes. Interrupts are efficient — the CPU can do other work and be notified only when needed — but they make a program much harder to reason about, because that jump can happen between any two machine instructions.
📖New term Interrupt Descriptor Table (IDT) and the IF flag. To use interrupts, a kernel must build an IDT: a table telling the CPU which handler function to jump to for each kind of interrupt. The CPU also has an interrupt-enable flag (IF) in its flags register; when IF = 0, the CPU ignores device interrupts entirely. Diamond keeps IF = 0 forever and never builds an IDT at all.

So Diamond's main loop, and every driver's "did anything happen?" function, works like this: to read a key, call kb_getchar(), which looks at the keyboard hardware once and returns a key if one is waiting, or "nothing" if not. The shell calls it over and over. This is polling. The trade-off is easy to state:

Interrupts (the normal way)Polling (Diamond's way)
How you learn of eventsHardware jumps you to a handlerYou repeatedly ask the hardware
CPU efficiencyHigh — CPU can sleep until neededLower — CPU keeps checking
Code complexityHigh — handlers fire between any two instructions; need locks, an IDT, careful re-entrancyLow — everything happens in plain, top-to-bottom order
Good forProduction systems that must be efficientA system you want to understand

Because Diamond only ever runs a person typing at a prompt, "wasting" a CPU core spinning in a poll loop costs us nothing we care about, and buys enormous simplicity: there are no interrupt handlers to write, no subtle timing bugs where a handler fires halfway through an update, and the whole system reads like an ordinary single-threaded program. Keep this rule in mind — every time you wonder "why doesn't it just wait for an interrupt here?", the answer is always "because Diamond polls."

🧭One real cost, previewed Polling does bite us once. A timer chip that a normal kernel would read via interrupts has to be read by hand in Diamond, and on some virtual machines that chip is silent — which once made the beep command hang forever. We fix it properly in Chapter 13. It is a good example of the polled rule having real consequences.

📖New terms Firmware is software baked into a chip on the motherboard that runs the instant the CPU powers on; on PCs it is called BIOS (older) or UEFI (newer). Its job is to test the hardware and then load a bootloader from a disk. A bootloader is a small program whose only job is to load the real operating system and jump into it.

Writing the firmware and early boot code yourself is possible but enormously tedious — it means dealing with the CPU's ancient 16-bit start-up mode, switching it step by step into modern 64-bit mode, and probing memory by hand. Diamond skips all of that by using an existing, excellent bootloader called Limine. Limine does the grubby early work and, by the time it calls us, has already:

  • switched the CPU into full 64-bit mode;
  • turned on the graphics screen and told us where its pixels live in memory;
  • figured out how much RAM the machine has and which parts are usable;
  • and mapped memory in a convenient way (the "higher-half" and "HHDM" layout, explained in Chapter 6).

The way Diamond and Limine talk to each other — Diamond asks for these facts and Limine answers — is the subject of the next chapter but one. First, the tools that turn our C into a kernel Limine can load.

3The toolchain: turning C into a kernel

You cannot build an operating system with the same compiler settings you use for an ordinary program, because an ordinary program leans on the operating system that Diamond is trying to replace. This chapter explains what "compiling for bare metal" means and walks through Diamond's actual build.

3.1  Why the normal C library is off-limits

When you write printf("hi") in a normal C program, printf is not really written by you — it comes from the C standard library, and deep down it makes a system call to ask the OS to write to the screen. Same with malloc (asks the OS for memory) and fopen (asks the OS for a file). Every one of those assumes an OS underneath.

Diamond is the thing underneath. So it cannot use any of that. Compiling in this mode — no standard library, no assumptions about an OS — is called building for a freestanding environment (as opposed to a hosted one, which has a full C library and an OS host).

📖New term Freestanding vs. hosted. The C standard itself defines these two modes. A hosted program starts at main() and may use the whole standard library. A freestanding program (the kind used for kernels) may use only a tiny handful of headers that define types but require no OS — such as <stdint.h> (the uint32_t family) and <stddef.h> (for size_t and NULL). Everything else — string functions, memory allocation, input/output — you must write yourself. Diamond does.

3.2  The compiler flags, one at a time

Here are the exact options Diamond passes to gcc for every kernel source file. They look cryptic, but each one is switching off an assumption that only makes sense when an OS is present.

The four that are genuinely OS-specific and worth understanding:

  • -ffreestanding and -nostdlib -nostdinc are the heart of it: no C library, no standard headers, no hidden calls into an OS. If Diamond wants strcmp, it writes its own (you will see k_streq later — the k_ stands for "kernel").
  • -mcmodel=kernel tells the compiler that our code will be loaded very high in memory (the "higher half" — Chapter 6). Without this, the compiler generates address math that only works for code in the low 2 GB, and the kernel crashes instantly.
  • -mno-red-zone turns off a small optimization (the "red zone") that is only safe when the CPU's interrupt machinery is set up a certain way. Since Diamond has no interrupt handlers, leaving it on could let stray hardware activity corrupt the stack. Off it goes.
  • -fno-pie -fno-pic ask for code that expects to run at one fixed address rather than code that can be slid around in memory. A kernel is loaded at a known place, so the simpler fixed-address form is exactly right.
🧭One flag exists only to keep GCC honest The Hyper-V driver is compiled with two extra flags, -fno-tree-loop-distribute-patterns -fno-builtin. Here is the trap they avoid: if you write a simple for loop that zeroes an array, GCC is clever enough to notice "that's just memset" and replace your loop with a call to the library function memset — which, in a freestanding kernel, does not exist, so the program fails to link. These flags tell GCC: don't be clever, run my loop as written.

3.3  Linking, and what an "ELF" is

Compiling turns each .c file into an object file (.o): machine code with the addresses not yet finalized. Linking stitches all the object files into one finished program and decides the final address of everything. The result is a single file, kernel.elf.

📖New term ELF. "Executable and Linkable Format" — the standard file format for programs on Linux and many other systems. An ELF file is machine code plus a header that says "load this chunk at this address, that chunk at that address, and start running at this entry point." Limine understands ELF, so Diamond's whole job at build time is to produce one correct ELF file for Limine to load.

Exactly where each piece of the kernel lands in memory is dictated by a linker script (kernel/linker.ld), which we will read in the next chapter — it is the file that says "the kernel lives at address 0xffffffff80000000 and starts at the function kmain."

3.4  Smuggling data into the kernel with objcopy

Diamond needs some non-code data baked in: a font file (so it can draw letters) and a few sound samples (so the piano can make noise). There is no filesystem to load them from at run time — Diamond has no disk driver. The trick is to convert each data file into an object file at build time and link it in, as if the bytes had always been part of the program.

The tool objcopy wraps the raw bytes and automatically defines three symbols the C code can refer to: _binary_..._ttf_start, _binary_..._ttf_end, and a size. Diamond's font code simply says "the font begins at _binary_..._ttf_start" and reads it straight from memory. We meet the other side of this in Chapter 8.

A bare ELF is not yet a bootable disk. Two final packages are produced, for two different situations:

4Booting: from power-on to kmain

We left the story at "Limine loads kernel.elf and jumps into it." This chapter fills in exactly where the kernel lands in memory, how it asks Limine for the facts it needs, and what the first function does. By the end you will have read Diamond's real entry point line by line.

🔬Going deeper: how Hyper-V actually launches this disk Chapter 3 said the .vhdx "installs Limine two ways." Here is the concrete mechanism, because it is why Diamond boots on Hyper-V at all. The .vhdx is a real GPT disk with a single FAT32 partition tagged as an EFI System Partition (ESP). Into that partition the build drops three things: Limine's UEFI program at the fixed path \EFI\BOOT\BOOTX64.EFI, the text config \boot\limine\limine.conf, and our kernel.elf.

A Generation 2 Hyper-V VM is a pure UEFI machine — no legacy BIOS, and (this matters later) no PS/2 keyboard. At power-on its UEFI firmware follows the standard fallback rule for a fresh disk with no saved boot entry: find the first ESP and run \EFI\BOOT\BOOTX64.EFI. That file is Limine. Limine then reads limine.conf, loads kernel.elf into the higher half, brings up the framebuffer, and jumps to kmain — precisely the handshake described just below. Diamond itself never speaks to firmware; Limine always stands between them.

The same image also gets limine bios-install written to its boot sectors, so a Generation 1 VM (legacy BIOS) boots the identical disk through Limine's BIOS path instead. One image, two firmwares.

Diamond's tested target is Gen 2: create the VM with Secure Boot OFF (Limine's BOOTX64.EFI is not signed with Microsoft's UEFI keys, so Secure Boot would reject it). And because Gen 2 has no PS/2 keyboard, the keys you type in the VM window arrive over the Hyper-V synthetic keyboard on VMBus — the driver we build in Chapter 13.

📖New term The "higher half." A 64-bit CPU can address a staggering range of memory. By universal convention, kernels live in the top part of that range (addresses starting with lots of f's) and leave the bottom part for programs. Even though Diamond has no user programs, it follows the convention because the tools and the boot protocol expect it — and it is why we compiled with -mcmodel=kernel back in Chapter 3. The physical RAM chips are of course much smaller than this address; a later mechanism (paging) maps this high virtual address down to real memory.
🧭Why the permissions matter to us later That "code is not writable, data is not executable" split is normally just good hygiene. But in Chapter 13 it becomes a real obstacle: the Hyper-V driver must build a small piece of executable code at run time, and it cannot put it in a data section (not executable) — so it has to smuggle it into .text. Keep this split in mind.

4.2  The Limine handshake: requests and responses

Diamond needs several facts from Limine: where the screen's pixels are, how much RAM exists, how many CPU cores there are, and so on. The way it asks is elegant and worth understanding, because you will see the same pattern used for every piece of boot information.

Diamond declares a set of request structures in a special section called .limine_requests. Each request is a little form that says "I would like to know X," with a blank response field. Before jumping to kmain, Limine scans that section, recognizes each request by its id, and fills in the response pointer with the answer. So by the time our code runs, the forms are already filled out.

The strange-looking __attribute__((used, section(".limine_requests"))) is a GCC instruction meaning "put this variable in the section named .limine_requests, and do not delete it even if it looks unused." That is what lands them in the spot the linker script set aside for Limine to find.

🔗Analogy Think of the requests section as a stack of forms you leave on the counter before the office opens. Limine is the clerk who arrives first, reads each form, writes the answer at the bottom, and leaves the stack for you. When you (kmain) walk in, you just read the answers.
📖What's inside one request Each request struct has three parts, all defined in Limine's header limine.h: an .id (a fixed set of magic numbers that uniquely names which question — like a form's title), a .revision (which version of the form you're using, so the protocol can evolve), and a response pointer that starts as NULL. Limine fills that pointer in with the answer. For the framebuffer, the response it points to holds the screen count and, for each screen, its address, width, height, and pitch — exactly the numbers the video chapter needs. So your code's job is just: check fb_req.response isn't NULL, then read those fields.

Diamond leaves six such forms: framebuffer (the screen), memory map (the RAM layout), HHDM and kernel address (two memory facts used in Chapter 6), SMP (the other CPU cores, Chapter 10), and module (for optionally loading extra data). It also declares which version of the boot protocol it speaks (LIMINE_BASE_REVISION(2)).

5Talking to hardware 101

Every driver in Diamond — screen, keyboard, sound, network — ultimately does one of two things: it reads or writes a hardware register through an I/O port, or it reads or writes hardware memory directly. Learn these two mechanisms once here, and every driver in the rest of the document becomes readable.

📖Warm-up: the bit operations you'll see everywhere Hardware is controlled one bit at a time, so from here on the code uses C's bit operators constantly. If these are new, this is all you need. Numbers written 0x.. are hexadecimal (base 16, where each digit is 4 bits), and every value is really a row of bits.
  • x << n ("shift left") moves bits left, adding n zeros on the right — so 1 << 4 is the number with only bit 4 set (binary 10000 = 16). Shifting right x >> n is the reverse; v >> 8 pulls out the "next byte up."
  • a & b ("and") keeps only bits set in both. Used to test a bit (x & 0x20 is nonzero only if bit 5 is set) or to mask — keep some bits, zero the rest (v & 0xff keeps just the low byte; addr & ~0xfff clears the low 12 bits to round down to a page).
  • a | b ("or") sets bits: flags | 1 turns bit 0 on, leaving the rest alone.
  • ~x ("not") flips every bit, so ~0xfff is "all ones except the low 12" — the mask that clears them in the example above.
  • a ^ b ("xor") toggles: a bit is set in the result only if it differs in the two inputs. We use it once to make Caps Lock invert Shift.
That is the entire vocabulary. Whenever you see one, translate it to "set / clear / test / keep this bit."

5.2  Way two: memory-mapped I/O (MMIO)

Ports can only carry one to four bytes at a time, which is far too slow for something like a screen with millions of pixels. So the other mechanism maps a device's memory (or registers) into the ordinary address space. Then you talk to the device by reading and writing memory with plain pointers. This is called memory-mapped I/O.

📖New term Memory-mapped I/O (MMIO). A region of the normal address space that is wired not to RAM but to a device. Writing to that address changes the device; reading from it queries the device. The screen's pixels are the classic example: there is a block of addresses where each 4 bytes is one pixel's color, and storing a number there lights up that pixel. Because it is "just memory" to the CPU, you access it with an ordinary (but volatile) pointer.

There is one problem left. To use a device you need to know its port numbers or its MMIO address — but those differ from machine to machine. How does a driver find its device and learn where it lives? The answer, for almost every modern device, is PCI.

📖New term PCI. The standard system that connects devices (graphics, network, sound, storage) to the CPU on essentially every PC. 6Memory: the map, the heap, the caches

Diamond has no operating system to give it memory, so it must manage RAM itself. This chapter covers three things: how a high virtual address reaches real RAM, how Diamond writes its own malloc, and one subtle trap about CPU caches that every device driver has to avoid.

6.1  Virtual vs. physical addresses

You met a puzzle in Chapter 4: the kernel is placed at address 0xffffffff80000000, which is far larger than the few gigabytes of RAM a real machine has. The resolution is that the addresses your code uses are not the addresses of the physical memory chips.

📖New terms Physical address = the actual location on the RAM chips (0 up to however many gigabytes you have). Virtual address = the address your code actually uses. A hardware unit in the CPU, the MMU (Memory Management Unit), translates every virtual address your program touches into a physical one, on the fly, using lookup tables called page tables. Memory is handled in 4 KiB chunks called pages. This indirection is called paging, and it is what lets the kernel sit at a huge virtual address while really living in ordinary low RAM.
🔗Analogy Virtual addresses are like a company's phone extensions. You dial extension 8000 (a virtual address); the switchboard (the MMU) connects you to whichever physical desk phone is currently assigned to that extension. The caller never needs to know the real wiring, and the same extension can be re-pointed to a different desk.

The good news for us: Limine sets up sensible page tables before kmain runs, so paging is already working. Diamond rarely has to touch page tables at all — with one exception in §6.5.

Before zooming into the details, here is the entire 64-bit virtual address space at a glance. Two things surprise newcomers: it is almost unimaginably larger than the few gigabytes of real RAM, and a vast chunk in the middle is actually illegal to use. Diamond occupies just two modest regions near the very top.

📖New term Canonical addresses & the non-canonical hole. Today's x86-64 chips don't actually wire up all 64 address bits — only the low 48 are translated, and the hardware demands that the top 16 bits all copy bit 47 (a kind of sign-extension). Addresses that obey this rule are canonical; the enormous middle range that doesn't is the non-canonical hole, and merely using such a pointer faults instantly. That single rule is what splits usable memory into a lower half (0x0 … 0x00007fffffffffff) and a higher half (0xffff800000000000 … top), with a permanent no-go zone between them. Diamond only ever lives in the higher half.

Now the centerpiece. kmalloc(n) must return a pointer to n unused bytes; kfree(p) must give them back. Diamond uses the classic, very teachable design: a first-fit free list.

The idea: carve the heap into a chain of blocks. Each block starts with a small header recording its size, whether it is free, and links to its neighbors. To allocate, walk the chain and grab the first free block big enough ("first fit"). To free, mark the block free and merge it with any free neighbors so the heap does not crumble into unusable slivers.

6.5  The cache trap, and the one time Diamond edits page tables

This section is the one genuinely subtle piece of memory management. You can skim it on a first read and come back, but every driver author eventually gets bitten by it.

📖New term CPU cache, and "write-back" vs "uncacheable." To be fast, the CPU keeps recently used memory in a small, quick cache and may delay writing changes back to real memory — a policy called write-back (WB). That is perfect for RAM. It is wrong for device memory (MMIO): if you write a command to a device but the CPU parks it in the cache instead of sending it, the device never sees it. Device memory must be marked uncacheable (UC) so every read and write goes straight through to the hardware, immediately and in order.

Here is the conflict. The convenient HHDM from §6.2 maps all memory as fast write-back. But some devices' MMIO regions are reachable only through that same mapping — so if Diamond talked to them through the HHDM, its commands could get stuck in the cache. The fix is ioremap_uc(): it edits the page tables so that one specific page is marked uncacheable, then returns a pointer safe for MMIO.

To do that it must walk the four-level page-table tree by hand. A 64-bit virtual address is really four 9-bit indexes (plus a 12-bit offset within the page), one for each level of the tree:

The two set bits PCD ("page cache disable") and PWT ("page write-through") are what mark the page uncacheable, and the final invlpg tells the MMU to forget any cached copy of the old translation so the new setting takes effect at once. Two small helpers keep the loop short. alloc_pt_page() just returns a fresh, zeroed 4 KiB page to use as a new table. split_huge() handles a rarer case: if a level already maps a giant huge page (2 MiB or 1 GiB, flagged by bit 7) it allocates a normal table, fills all 512 entries so they reproduce that same block at 4 KiB granularity (same start address stepping by 4 KiB, same flags), and replaces the huge entry with a pointer to that new table — after which the walk continues normally.

🔬Going deeper: reading a page-table entry Every entry (at every level) is a 64-bit number with the same shape: the top bits hold a physical address (always page-aligned, so its low 12 bits are free) and those low 12 bits hold flags. That is why the code masks with & ~0xFFFULL to extract just the address, and ORs in flag bits to set options. The ones Diamond touches:

4PCDpage cache disable — the other half of uncacheable

So (phys & ~0xFFFULL) | (1ULL<<4) | (1ULL<<3) | 3 reads as: "map this physical page, uncacheable, present, writable." Once you see entries this way, page tables stop being mysterious — they are just arrays of these numbers, 512 per 4 KiB table.
🔬Going deeper: huge pages For speed, Limine often maps memory in big 1 GiB or 2 MiB pages instead of many 4 KiB ones. But UC is a per-page property, and Diamond wants to make just one small page uncacheable without disturbing its neighbors. So ioremap_uc first splits a huge page into 512 smaller ones (the helpers split_1g and split_2m), then flips UC on only the single 4 KiB page it cares about. This is the kind of detail that a driver author must get exactly right and a reader can safely file under "handled."

7.1  What a framebuffer is

Limine's framebuffer request answered with four numbers: an address, a width, a height, and a pitch. The address points at a region of MMIO memory (Chapter 5) where each pixel is 4 bytes. Store a color there and that pixel lights up.

8Text: fonts, the terminal, and the serial console

A prompt needs letters, and letters are surprisingly deep. This chapter turns a font file into pixels, builds a scrolling text console on top, and adds a "serial" console — a second, text-only window that turns out to be a lifesaver when the graphical one is not available.

8.1  From rectangles to letters

In Chapter 7 we could fill rectangles. A letter is just a very particular pattern of filled and empty pixels — a glyph. We could hand-draw each letter as a tiny grid, but Diamond does something nicer: it reads a real TrueType font file (the same kind Windows and your phone use) and turns its mathematical outlines into pixels. It does this with a famous, tiny, single-file library called stb_truetype.

📖New terms Glyph = the picture of one character. TrueType = a font-file format that stores each glyph as smooth mathematical curves, so it can be drawn at any size. Rasterizing = converting those curves into a grid of pixels at a chosen size. stb_truetype = a well-known, dependency-free C library (a single header file) that does the rasterizing.

Rasterizing curves is slow, so Diamond does it a single time at startup and caches the result. A keyboard does not send letters. It sends numbered key events, and turning those into the character 'A' is the driver's job. This chapter does that, then shows Diamond's clever twist on the driver-table pattern — one that lets several completely different keyboards work at the same time.

9.4  The mouse, briefly

The piano demo (Chapter 12) needs a pointer, so Diamond also has a PS/2 mouse driver. It works just like the keyboard: the mouse sends fixed 3-byte packets (button states, and how far it moved in x and y since last time), and the driver polls the same i8042 controller, distinguishing mouse bytes from keyboard bytes by a status bit. It keeps a running cursor position, clamped to the screen. Two small realities it has to handle are worth noting, because they are the kind of thing that only shows up on real hardware:

  • PS/2 reports "y increases upward," but screens number rows downward, so the driver negates y.
  • It resets the mouse at startup to force simple 3-byte packets, because some emulators otherwise leave it in a 4-byte "scroll wheel" mode that would desynchronize every reading.

The two "realities" above are visible right in the code: the -256 trick reconstructs a negative movement from the 8-bit magnitude and its sign bit, and the leading - on dy flips PS/2's upward-positive convention to the screen's downward-positive rows.

Like every other input source, the mouse is polled — the shell or a demo calls mouse_poll() when it wants the latest position; nothing interrupts.

10Using every CPU core

Your computer has several CPU cores, but so far Diamond has used exactly one. This chapter wakes the others up, gives them work, and confronts the danger that comes with shared memory — the reason the terminal needed a lock. This is the machinery that lets the ray tracer run four times faster.

10.1  One core is awake; the rest are asleep

When a PC boots, only one core is running — by tradition it is called the BSP (bootstrap processor). The others, the APs (application processors), sit halted until someone tells them to start. Waking them at the raw-hardware level is fiddly, but — as with everything early-boot — Limine did the hard part. Its SMP response hands us a list of the cores, and for each sleeping AP there is a magic slot: write the address of a function into goto_address, and that core springs to life running your function.

📖New terms SMP = "Symmetric Multi-Processing," several equal CPU cores sharing one memory. Core / CPU. An independent processor that executes instructions; a modern chip has several. BSP / AP. The one core that starts running at boot (bootstrap processor) versus the others that must be woken (application processors). LAPIC ID. A small number that uniquely identifies each core, so code can ask "which core am I running on right now?"

10.2  What each AP does when it wakes

Diamond gives every AP the same tiny life: enable SSE math (each core must do this for itself), announce "I'm online," then loop forever waiting for a job. A "job" is just a function pointer and an argument left in that core's slot; when one appears, the AP runs it and sets a "done" flag.

📖New syntax: a function-pointer typedef typedef void (*work_func_t)(void *); reads inside-out: it defines a new type name, work_func_t, meaning "pointer to a function that takes one void * and returns void." After that line you can keep a function in a variable (work_func_t f = render_worker;) and later call it (f(arg);) — exactly how one core hands a job to another.
📖New keyword: volatile volatile tells the compiler "this memory can change behind your back — always re-read it, never cache it in a register." It is essential here because one core writes work_fn while another core is spinning on it; without volatile the compiler might read it once and loop forever on the stale value. (It is not a substitute for the barriers and atomics we cover next — it only stops the compiler from optimizing the access away.)

The BSP, meanwhile, starts each AP and then waits until all of them have set online = 1 before moving on — so by the time smp_init returns, every core is awake and idling, ready for work:

Dispatching work later is symmetric. smp_dispatch fills a core's slot and smp_wait spins until that core reports done — a matched pair with the AP's work loop above:

Notice the ordering: smp_dispatch writes work_arg before work_fn, and the AP's loop reads work_fn before touching work_arg — so the argument is always in place by the time the job pointer becomes visible. The ray tracer in Chapter 12 uses exactly this to farm out rows of the image to the other cores.

10.3  The danger of sharing: race conditions

The instant two cores touch the same memory, a new class of bug appears. Suppose two cores both run count = count + 1. That is really three steps: read count, add one, write it back. If both cores read 5 before either writes 6, both write 6 — and one increment is silently lost. This is a race condition, and it is the reason the terminal (Chapter 8) guards its drawing.

📖New terms Race condition. A bug where the result depends on the exact timing of two cores accessing shared data — usually because an operation that looks like one step is really several. Atomic operation. A special instruction guaranteed to happen all-at-once, so no other core can catch it half done. Memory barrier. An instruction (__sync_synchronize() above) forcing the CPU to actually finish earlier memory writes before later ones — because cores are otherwise allowed to reorder writes for speed, which can make one core see another's updates out of order.

10.4  The spinlock

The classic fix is a lock: a rule that only one core at a time may enter a critical section. Diamond uses the simplest kind, a spinlock. To take the lock, a core atomically sets a flag to 1 and checks what it was: if it was 0, this core got the lock; if it was already 1, someone else holds it, so the core "spins" — loops — until it turns back to 0. To release, set it back to 0.

📖New term Test-and-set. __sync_lock_test_and_set(l, 1) is a GCC built-in that compiles to a single atomic hardware instruction: it stores 1 into *l and returns whatever was there before, with no gap for another core to sneak in. That indivisibility is exactly what a lock needs. The inner "while (*l) pause" is an optimization — spin on a cheap read until the lock looks free, then attempt the expensive atomic write — but the correctness all comes from that one atomic test-and-set.
⚠️Gotcha: a spinlock burns a whole core while it waits A spinlock does not sleep — a core waiting for one loops uselessly, doing nothing but checking. That is fine when locks are held for a few microseconds (like drawing one character) and disastrous if held for long. It also means you must never take the same lock twice on one core, or hold a lock while waiting for something that needs it — the core would spin forever. Keep critical sections short; that is the whole discipline.

Now the terminal's lock → draw → unlock from Chapter 8 makes complete sense: when the BSP and an AP both print (the ray tracer's status lines, say), the lock serializes them so their pixels never interleave. One small header, used in one place, and multi-core text output is safe.

Sound is the same driver-table story as video — probe for the best device, keep it, fall back to something that always works. But it hides one of the most instructive bugs in the whole project: a beep that never returned. Chasing it teaches you exactly what "no timer, fully polled" costs.

11.1  The audio driver table

11.2  The PC speaker: a square wave from a timer chip

The PC speaker can only do one thing: be on or off. To make a tone, you flip it on and off very fast — hundreds or thousands of times a second — and your ear hears that flicker as a pitch. Rather than toggle the speaker by hand, the PC wires it to a channel of an ancient timer chip, the PIT (Programmable Interval Timer). You tell the PIT "oscillate at frequency F," connect it to the speaker, and it produces a steady square wave with no further help from the CPU.

📖New term PIT (Programmable Interval Timer). A chip (the 8254) with a fixed 1,193,182 Hz clock and three "channels" that each divide it down. Channel 2 drives the speaker; give it a divisor and out comes 1193182 / divisor Hz. So to play 440 Hz you write divisor 2712. The two outbs send the divisor one byte at a time because the port is only 8 bits wide.

So beep is simply: turn the speaker on at a frequency, wait the requested number of milliseconds, turn it off. Everything interesting is hiding in that one word, "wait."

11.3  A war story: the beep that never returned

How do you wait exactly 200 milliseconds when you have no interrupts and no clock ticking in the background? On a normal PC, Diamond reads a different PIT channel (channel 0), which counts down continuously at that same 1.19 MHz. You snapshot the counter, then loop reading it, adding up how far it has moved, until enough ticks have gone by. Polling a counter to measure time — very much in the spirit of this whole OS.

That worked perfectly under QEMU. Then Diamond booted on real Hyper-V, someone typed beep… and the shell froze forever. The demo (videodemo, the ray tracer) had all worked; only beep hung. Why?

⚠️The bug On a Hyper-V "Generation 2" virtual machine, the legacy PIT channel 0 is not a functioning counter — it never advances. Diamond's wait loop kept reading the same value, decided that zero time had passed, and looped… forever. The speaker was even correctly turned on; the code just never reached the line that turns it off. A wait loop that assumes its clock ticks will hang on any machine where that clock is dead.

The fix has two halves, and both are worth remembering. First, when Diamond is on Hyper-V, use a clock that Hyper-V guarantees works — the hypervisor's own reference counter (more on Hyper-V in Chapter 13). Second, make the old PIT fallback give up instead of hang: count how many times in a row the counter fails to move, and after a large but finite number of tries, just return.

🧭The lesson, restated Chapter 2 promised that "fully polled" has a price and named this exact bug. Here it is in the flesh: with no timer interrupt, you own timekeeping, and every wait loop must survive a clock that isn't ticking. On Generation 2 Hyper-V the speaker is silent anyway (that VM emulates no sound hardware) — but now beep at least returns, and the shell lives on.

11.4  Real samples: PCM

A beep is a pure tone. Playing an actual recording — a piano note — means streaming PCM: thousands of little numbers per second, each the speaker-cone position at that instant. The PC speaker cannot do this (its play_pcm just returns -1), but a real HD Audio codec can, and that is what the piano demo in the next chapter uses. The driver table means the piano does not care which one it got: it calls audio_play_pcm(...) and either hears music or a polite "not supported."

📖New term PCM (Pulse-Code Modulation). The plainest way to store sound: measure the wave's height many thousands of times a second (Diamond's samples are 44,100 times a second) and save each measurement as a number. Play them back at the same rate and you reconstruct the sound. It is exactly what a .wav file holds.
🔬Going deeper: how the HD-Audio driver actually plays PCM (and our honest boundary) The PC speaker is driven one bit at a time by the CPU. A real sound card can't be — 44,100 stereo samples a second is far too many to hand over one at a time. Instead it uses DMA (direct memory access): you place your samples in a buffer in RAM, give the card a small list of such buffers (a "buffer descriptor list"), and the card's own hardware walks that list, fetching samples and clocking them out at the sample rate without the CPU. Diamond's job shrinks to: keep the buffers full, and check a position register to see which buffer the card has finished so it can refill it — polling again, just like everything else. The exact sequence of register writes and "codec verbs" that wakes an Intel HD-Audio codec up is long, vendor-specific, and beyond the scope of this book; it lives in drivers/audio/hda.c if you want to read it. The takeaway you do need: if you re-implement Diamond, build sound on the PC speaker shown above (it is complete on this page) and treat HD Audio as an optional upgrade — the driver table means the piano demo runs either way, with music or a polite "not supported."

12The shell and the demos

Every piece now exists: video, text, keyboard, memory, cores, sound. The shell is the thin layer that lets a human drive them, and the demos are where the pieces combine into something that feels alive — most of all a ray tracer that gets four times faster when you type its name a second time.

12.1  The shell is just a loop

Remember the big idea from Chapter 2: there is no "operating system" for the shell to call into. The shell is the program, and it calls drivers as ordinary functions. Its whole structure is: print a prompt, read a line, compare it against known commands, run the matching one, repeat forever.

That is the entire line editor: printable characters are echoed and stored, Backspace erases, Enter finishes the line. Notice it uses only term_getchar and term_putchar from Chapter 8 — the shell has no idea whether the keystroke came from a real keyboard, the Hyper-V synthetic keyboard, or the serial port. The layers you built are paying off.

🔬Going deeper: is this if/else chain "good"? It is a long ladder of else ifs, and a common instinct is to replace it with a table of {name, function} pairs looped over — the exact idea you saw for drivers. For a shell it is a genuine judgment call: the table is tidier and data-driven, but the ladder is trivially readable, handles odd cases easily (echo  matches a prefix, beep 440 passes an argument), and there are only a couple dozen commands. Diamond keeps the ladder. Recognizing that both are reasonable — and why — is more valuable than mechanically applying the table pattern everywhere.

12.2  The showcase: a parallel ray tracer

Ray tracing makes a realistic image by simulating light: for every pixel, shoot a ray into a 3-D scene, see which sphere it hits, and compute its color from the lighting, shadows, and reflections. Diamond's tracer renders six shiny spheres with shadows and two bounces of reflection. It is also pure math on independent pixels — which makes it the perfect way to show off multiple cores.

The trick is dynamic scanline stealing. Instead of pre-assigning rows to cores (some rows are cheap sky, some are expensive reflective spheres — an uneven split), all cores share one atomic counter. Each core repeatedly does "give me the next row" — an atomic add — and renders that row, until the rows run out. Fast cores naturally grab more rows; nobody sits idle. This is exactly the smp_dispatch / smp_wait machinery from Chapter 10 put to work.

The raytrace command renders the scene twice — once on a single core, once on all of them — timing each with rdtsc (a counter of CPU cycles) and printing the speedup. On a 4-core VM you watch it finish roughly 4× faster the second time, with a per-core tally of how many rows each stole. That number is the whole book paying off at once: boot, memory, video, and multi-core all cooperating.

📖New terms Ray tracing. Rendering an image by tracing the path of light rays through a scene, pixel by pixel. RDTSC. "Read Time-Stamp Counter" — an x86 instruction returning how many cycles the CPU has run; dividing two readings gives elapsed time in cycles, perfect for measuring a speedup. Atomic add. __sync_fetch_and_add(&n,1) adds one and returns the old value as one indivisible step, so two cores can never grab the same row.
🔬Going deeper: what "trace every pixel" actually computes Inside that loop, each pixel is one ray, and the whole scene is just spheres, so the math is high-school algebra and vectors:
  1. The ray is a moving point P(t) = O + t·D: start at the eye O, travel in direction D (pointed at this pixel). t is how far along you are.
  2. Hit test. A sphere of center C, radius r is all points where |X − C|² = r². Substitute the ray for X and you get a plain quadratic a·t² + b·t + c = 0 with a = D·D, b = 2·D·(O−C), c = (O−C)·(O−C) − r². If the discriminant b²−4ac is negative the ray misses; otherwise the smaller positive root t is the nearest surface point. (· is the dot product, x₁x₂+y₁y₂+z₁z₂.)
  3. Shade it. At the hit point the surface normal is N = (hit − C)/r. Diamond uses Blinn-Phong lighting: color = a little ambient + diffuse max(0, N·L) (bright where the surface faces the light L) + a specular highlight max(0, N·H)ⁿ (the shiny dot, where H is the halfway direction between light and eye).
  4. Shadows & mirrors. Shoot one more ray from the hit toward the light — if it hits another sphere first, this point is in shadow. Then reflect the ray about N and trace that to get the mirror image; Diamond bounces twice.
This is textbook "Whitted" ray tracing. The only helpers are three short vector functions (dot, normalize, reflect) in raytrace.c; with the four steps above you have everything needed to re-derive them.

12.3  The piano: pixels, mouse, and sound together

The piano command draws all 88 keys, tracks the mouse (Chapter 9) as a crosshair, and plays a note when you hold Space over a key. It uses only six real recordings — one every octave (A1, A2, … A6), baked into the binary at build time with objcopy, just like the font. To hit the other 82 keys, it pitch-shifts the nearest recording.

Pitch-shifting is beautifully simple here: to play a note higher, read through the recorded samples faster. The step size is stored as a Q16.16 fixed-point number (top 16 bits = whole part, bottom 16 = fraction) because there is no floating point in this path — the whole part indexes the sample, and adding the step each output frame walks through the source at the right speed.

📖Where the step comes from For a shift of s semitones the step is ratio = 2(s/12) × 65536, rounded to a whole number. Twelve semitones is one octave and doubles the pitch, so s = 12 gives 2 × 65536 — read the sample twice as fast. The × 65536 (that is, × 216) is what puts the value in Q16.16 form. All 25 steps for s = −12…+12 are computed once into a table at build time, so this inner loop does nothing but an integer add per frame.
🧭Why kb_space_held() and not getchar? The shell reads characters, but the piano needs to know whether a key is still down right now — a different question. In a polled system with no key-up events from the terminal layer, the piano peeks directly at the keyboard hardware between audio chunks. It is a small, honest exception, and a good reminder that "keyboard input" can mean more than one thing.

13Running under Hyper-V

Everything so far works on QEMU. Then you boot Diamond on Microsoft Hyper-V's modern "Generation 2" virtual machine and the keyboard is dead — because that machine has no keyboard, not even a fake one. Getting a keystroke here means speaking the hypervisor's own private protocol. This is the hardest driver in the book, and the most rewarding.

13.1  Why the keyboard vanished

Older virtual machines emulate real chips: the VM pretends to contain the same 40-year-old keyboard controller a physical PC has, so your PS/2 driver from Chapter 9 just works. A Hyper-V Generation 2 VM throws all that legacy away. There is no emulated PS/2 controller, no emulated USB, not even a working legacy timer (that was the beep bug in Chapter 11). Instead the keyboard is a synthetic device: the guest and the hypervisor talk over a fast software channel called VMBus. No VMBus driver, no keys.

📖New terms Hypervisor. The software that runs virtual machines (Hyper-V is Microsoft's). Paravirtualization. Instead of imitating old hardware, the hypervisor offers fast, purpose- built channels and expects the guest to cooperate by speaking its protocol. Synthetic device. A "device" that exists only as that protocol — no chip, real or emulated, behind it. VMBus. Hyper-V's message-and-ring-buffer bus connecting a guest to synthetic devices.
🔗Analogy Emulation is a robot hand pressing keys on a real keyboard so your old software feels at home. Hyper-V's synthetic keyboard skips the theater: it hands you a phone line and says "just tell me you want keystrokes and I'll read them to you." Faster and cleaner — but only if you know how to dial.

13.2  Talking to a hypervisor without interrupts

Normally VMBus is interrupt-driven: the host raises an interrupt when a key is ready. But Diamond runs with interrupts off and no interrupt table at all (Chapter 2). So Diamond does what it always does — it polls. It sets everything up so the host would interrupt, then simply ignores the interrupt and reads the shared memory the host writes into. Two tools make this possible:

  • A hypercall — a function call into the hypervisor, used to send messages to the host (the guest→host direction).
  • The SynIC and its shared pages plus per-channel ring buffers — memory the host writes into, which the guest reads (the host→guest direction).

Ordinary hardware has a handful; Hyper-V exposes its whole control surface as a block of them (for example number 0x40000000 is "guest OS id," 0x40000083 is "put the message page here"). 📖New term Ring buffer. A fixed-size byte array shared by two parties, with two counters: write_index (how far the writer has filled) and read_index (how far the reader has consumed). 15Glossary

Every term introduced in a 📖 box, in one place. Skim it now; return whenever a word stops you. The chapter tag points to where the idea is explained in full.

Alpha blending
Mixing a semi-transparent pixel with the one behind it so edges look smooth; each pixel carries an "alpha" (coverage) value. Chapter 8
Application processor (AP)
Any CPU core other than the one that starts at boot; it must be explicitly woken. Chapter 10
Atomic operation
A machine instruction guaranteed to complete all-at-once, so no other core can observe it half-done — the foundation of locks and shared counters. Chapters 10, 12
Bootstrap processor (BSP)
The single CPU core that is already running when the machine powers on. Chapter 10
Cross-compiler / toolchain
The compiler, assembler, and linker that turn your source into a program; "freestanding" means building for bare metal with no operating system underneath. Chapter 3
DMA (Direct Memory Access)
A device reading or writing RAM by itself, using physical addresses — which is why drivers must translate their pointers. Chapter 6
ELF
The standard file format for a compiled program on Unix-like systems; Diamond's kernel is an ELF the bootloader loads. Chapter 3
Exokernel
A design where the "OS" is just a library the application links against — no privileged kernel, no syscalls. Diamond's core idea. Chapter 2
Fixed-point (Q16.16)
Representing fractions with integers by reserving some bits for the fractional part (here 16), used where floating point is unavailable. Chapter 12
Framebuffer
A block of memory where each element is one pixel's color; writing to it changes the screen. Chapter 7
Freestanding
Compiling with no standard library or OS assumed — you get the language and little else. Chapter 3
HHDM (higher-half direct map)
A region where the bootloader maps all physical RAM, so phys + offset is always a usable pointer. Chapter 6
Heap / allocator
The pool of memory handed out at runtime, and the code (kmalloc/kfree) that manages it. Chapter 6
Higher half
Placing the kernel at a very high virtual address so low memory stays free for programs. Chapter 4
Hypercall
A call into the hypervisor — the guest's way to ask the host to do something. Chapter 13
Hypervisor
Software that runs virtual machines (Hyper-V, QEMU/KVM). Chapter 13
IDT (Interrupt Descriptor Table)
The table telling the CPU where to jump on each interrupt or fault. Diamond has none, so it never takes interrupts — and any fault reboots it. Chapter 2
Interrupt
A hardware signal that yanks the CPU away to handle an event. Diamond turns them off and polls instead. Chapter 2
I/O port
A separate little address space for talking to old-style devices, reached with the in/out instructions. Chapter 5
LAPIC ID
A small number uniquely identifying each CPU core. Chapter 10
Limine
The bootloader Diamond uses; it loads the kernel, sets up a framebuffer and memory map, and hands over control. Chapter 4
Linker script
A recipe (linker.ld) telling the linker what address each part of the program lives at. Chapter 4
Memory barrier
An instruction forcing earlier memory writes to complete before later ones, so other cores see updates in the right order. Chapter 10
MMIO (memory-mapped I/O)
Talking to a device by reading and writing special memory addresses; must use volatile so the compiler doesn't optimize the accesses away. Chapter 5
Objcopy
A tool that turns any file (a font, an audio clip) into a linkable object so it can be embedded in the binary. Chapters 3, 8
Paging / page table
The CPU mechanism that maps virtual addresses to physical ones, in 4 KiB pages, via tables in memory. Chapter 6
Paravirtualization
A guest cooperating with the hypervisor over purpose-built channels instead of pretending to be legacy hardware. Chapter 13
PCI / config space
The bus most devices sit on, and the standard table describing each device (vendor, type, memory regions). Chapter 5
PCM (pulse-code modulation)
Sound stored as many amplitude samples per second; replay them at the same rate to reconstruct the wave. Chapter 11
PIT (programmable interval timer)
An old timer chip; channel 2 drives the PC speaker's pitch, channel 0 can be polled as a clock. Chapter 11
Polling
Repeatedly checking a device "is there input yet?" instead of waiting for an interrupt. Diamond's universal strategy. Chapter 2
Probe
A driver's "are you there?" test; the first driver in a table that probes successfully is the one kept. Chapter 7
Race condition
A timing-dependent bug from two cores touching the same data at once. Chapter 10
Rasterize
Convert a shape's mathematical outline (like a font glyph) into actual pixels. Chapter 8
Ray tracing
Rendering by simulating light rays through a scene, one per pixel. Chapter 12
RDTSC
An instruction returning the CPU's cycle count; subtract two readings to time something. Chapter 12
Ring buffer
A fixed circular queue in shared memory; here the host writes keystrokes and the guest reads them. Chapter 13
Scancode
The raw numeric code a keyboard sends for a key press or release, before translation to a letter. Chapter 9
SMP
Symmetric multi-processing: several equal CPU cores sharing one memory. Chapter 10
Spinlock
The simplest lock: a core loops ("spins") until it can atomically claim a flag, guaranteeing one-at-a-time access. Chapter 10
SynIC
Hyper-V's synthetic interrupt controller; its shared pages are where VMBus messages land. Chapter 13
Synthetic device
A device that exists only as a hypervisor protocol — no chip behind it, real or emulated. Chapter 13
Test-and-set
The atomic "write 1, tell me the old value" operation a spinlock is built from. Chapter 10
UART / serial port
The COM1 chip that sends characters one bit at a time down a wire — Diamond's lifeline for debugging when the screen is blank. Chapter 8
VMBus
Hyper-V's software bus connecting a guest to its synthetic devices. Chapter 13
Volatile
A C keyword telling the compiler a value can change on its own, so every read/write to it must really happen — essential for MMIO. Chapter 5
Write-back vs uncacheable (WB/UC)
Whether the CPU may cache a memory region. Device memory must be UC so writes reach the hardware immediately. Chapter 6
